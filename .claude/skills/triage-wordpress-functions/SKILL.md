# Triage WordPress functions

Every WordPress function in `api/wordpress.json` must end up in exactly one place in `wpal.map.php`:

- **`services`**: wrapped by a `Service` (generated by `bin/wpal fix`), or
- **`ignore` / `ignore_files`**: deliberately not wrapped, with a short reason.

Private (`_`-prefixed, `@access private`) and deprecated functions are ignored automatically; never list them.

## Steps

1. See what's untriaged: `bin/wpal coverage --untriaged` (or `--format=json`, `untriaged` is grouped by source file).
2. For each function, read its docblock and signature: `php -r '$d=json_decode(file_get_contents("api/wordpress.json"),true); echo $d["functions"]["<name>"]["doc"];'`
   (keys use WordPress's spelling, e.g. `get_the_ID`).
3. Decide: wrap (which service?) or ignore (which reason?). Rules below.
4. Edit `wpal.map.php`: add names to the service's list under `services` (list order is method order; group related
   functions together), or add an `ignore` entry.
5. Run `bin/wpal fix`, then `bin/wpal coverage --fail-on-untriaged` (must report no problems), `bin/wpal check`, and `composer check`.
6. New PHPStan findings from WordPress's own docblocks go in the baseline:
   `vendor/bin/phpstan analyse --memory-limit=512M --generate-baseline phpstan-baseline.neon`. Findings in tool or Api
   code are real; fix them.

## Wrap or ignore?

Wrap anything a plugin or theme can reasonably call: getters, setters, registration functions, conditionals
(`is_*`), template tags, URL builders, formatting and escaping helpers, admin UI helpers used by plugins.

Ignore, with one of these reasons (reuse the wording so reasons group in `coverage`):

| Reason | Use for |
| --- | --- |
| `admin AJAX handler` | `wp_ajax_*` request handlers |
| `hook callback` | Functions WordPress only attaches to its own hooks (e.g. `wp_*_head` printers registered on `wp_head`, `*_init` callbacks on `init`) and that plugins have no reason to call |
| `internal callback` | Helpers WordPress passes to `preg_replace_callback()`/`array_map()` inside another function (e.g. `wp_rel_callback()`), not hooks |
| `bootstrap internals` | Request setup in `load.php`/`ms-load.php`, constant definitions, `wp_initial_constants()` and the like |
| `database upgrade step` | Versioned upgrade routines |
| `installer internals` | Install/upgrade/schema plumbing a plugin never calls (`wp_install()`, `populate_*()`, `make_db_current()`) |
| `admin screen internals` | Code that renders one specific core admin screen, e.g. dashboard widget and core meta box render callbacks |
| `PHP polyfill` | Re-implementations of PHP functions |
| `bundled library` | Functions of third-party code shipped in WordPress (PclZip, POP3, AVIF info) |
| `legacy` | Superseded APIs WordPress keeps without `@deprecated` (e.g. `rss.php`'s MagpieRSS) |

When in doubt, wrap: an unused method costs little, a missing one blocks users.

## Choosing a service

- **By domain, not by source file.** `functions.php` and `formatting.php` hold many domains; split them.
- **Reuse an existing service** when the domain matches (see `services` in `wpal.map.php`), e.g. more user meta goes
  where user functions go, not into `PostMeta`.
- **Create a new service** when a coherent domain of roughly 3+ functions has no home. Names: PascalCase plural noun or
  domain (`Users`, `Http`, `Cron`, `Rewrite`, `Sanitization`, `Escaping`, `Kses`, `Shortcodes`, `Blocks`, `Widgets`,
  `Multisite`, `Media`, `Images`, `Embeds`, `RestApi`, `Cache`, `Filesystem`, `Mail`, `Dates`, `Json`). Check the
  existing names first; don't create near-duplicates (`Urls` exists, so no `Links`).
- **Theme output** belongs in the `*Template` services (`PostTemplate`, `CommentTemplate`…), not domain services.
- **Admin-only helpers** plugins use (`add_meta_box()`, `submit_button()`, list-table helpers) go to admin services
  (`MetaBoxes`, `AdminTemplate`, …), keeping domain services front-end safe.
- Aim for services under ~100 methods; split big domains (e.g. `Sanitization` vs `Escaping` vs `Kses`).
